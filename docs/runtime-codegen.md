# Run-time code generation with the Class-File API

Without the protoc plugin, buff-json decodes with the *typed builder* decoder: per-field lambdas that call builder setters through method handles. It is 1.3–2.5× slower than the decoder the plugin generates, mostly because everything goes through shared call sites that the JIT cannot specialise per field. This document describes how that gap is closed at run time on Java 24+, and how the run-time and the build-time routes share one description of the generated code.

## Summary

- `BuffJson.decoder().setRuntimeCodegen(true)` (or `-Dbuffjson.runtimeCodegen=true`) generates, on first use of a message class that has no plugin-generated decoder, the same canonical-input reader (`readFast`) that the plugin would have generated. It is defined as a class next to the message class and is called exactly like compiled code. Off by default.
- **One description, two renderings.** `FastReaderTemplate` (in `buff-json`) describes the reader in a small typed code model (`Ty`, `Expr`, `Stmt`, `Members`). The protoc plugin *prints* it as Java (`SourcePrinter`); the runtime *lowers* it to bytecode with the Class-File API (`ClassFileBackend`, Java 24+). There is no second generator to keep in sync: the string-based `FastDecoderGenerator` (605 lines) became a 116-line adapter over the template.
- Compile-time and run-time decoders interoperate. A generated reader calls the plugin's decoder for a nested message that has one, and a run-time generated one for the rest — direct calls of constant instances that the JIT inlines. A plugin-generated parent whose child message class has no plugin decoder (a message from a dependency compiled without the plugin, such as `google.protobuf.SourceContext`) asks for a reader when it meets one.
- The reader only accepts *canonical* JSON; anything else makes it give up and the document is re-decoded by the general decoder of the same tier (the fast path contract is unchanged). Results, exceptions and messages are therefore exactly those of that general decoder.
- Everything is optional and falls back. Where the JVM has no Class-File API, the message class cannot be reached by a lookup, or anything at all fails, the message has no generated reader and decodes as before. A failed generation is remembered and never retried.
- Measured (JDK 25, next section): the generated reader is **1.7× as fast as the typed decoder** (geometric mean over the seven shapes it handles; 1.3–2.6× per shape, 1.6× on a mixed workload of six message types) and **as fast as the plugin's decoder** (0.99–1.02×, within noise). Documents that hold a `Struct` or `Any` bail out and cost 1–5% more than the typed decoder alone, exactly as with the plugin.

Reading the tables:

- The run-time generated reader is the same code as the plugin's, so parity with the plugin is the expected result and is what is measured; the gain over *typed* is what the plugin's readers give, without the plugin.
- Shapes with `Struct`/`Any` (marked *bails*) hold a value the fast reader does not read; those documents pay the aborted scan and then the general decode: 0.95–0.99× of the typed decoder alone, and the same as with the plugin (1.00×).
- Small scalar-heavy messages gain most (the per-call fixed cost and the per-field lambdas dominate the typed decoder); map- and repeated-heavy messages gain least (the time goes to creating strings and protobuf collections, which no reader avoids).

### The encoder was not ported

The same technique could generate encoders, but the potential is small: the typed-accessor encoder already binds typed getters with `LambdaMetafactory`, and on JDK 25 (UTF-8 output, `EncodePathsBenchmark`) it reaches 0.86× (simple), 0.89× (complex), 0.82× (map-heavy), 1.09× (`Struct`) and 0.84× (timestamps) of the plugin's throughput — a geometric mean of 0.90, so at most ~12% would be won. The model would first need `float`/`double` comparisons, `for` loops over repeated fields and a few runtime helpers (enum name tables, map iteration). Not worth it as a first step; the model and the backend are the place to start if that changes.

## Design

### The code model

`io.suboptimal.buffjson.internal.codegen` describes code the way both backends can consume it:

|              |                                                                                                                                                                          |
|--------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `Ty`         | primitives, classes (by binary name), arrays; knows its source spelling and JVM descriptor                                                                               |
| `Expr`       | literals, locals (`Var`), array loads, binary/unary operators with Java's numeric promotion, casts, static/virtual/interface calls, `new`, static fields, class literals |
| `Stmt`       | declarations, assignments, `if`, `while`, `switch` on `int`, `break`, `return`, `throw`, blocks: structured control flow only                                            |
| `Members`    | fields (static initialisers run in the class initialiser) and methods (with the erased return type when a bridge method is needed)                                       |
| `Block`, `E` | builders, so a template reads like the Java it produces                                                                                                                  |

Every expression carries its type, so neither backend infers anything. `SourcePrinter` writes Java (fully qualified names, minimal parentheses plus clarity parentheses for mixed bitwise/arithmetic operands, no redundant casts because the build uses `-Xlint:all -Werror`). `ClassFileBackend` writes what javac would: the same locals, jumps, switches (javac's `tableswitch`/`lookupswitch` choice) and calls, with the stack map frames worked out by the API.

### The template

`FastReaderTemplate` is the former string-based `FastDecoderGenerator` expressed in the model: a shell with a local position `p` and the document in a local `byte[] b`, an 8-way hashed member-name matcher for wide messages, one small static method per field, byte-exact enum matchers, and `bail()` for everything it does not accept. It asks its `Env` a handful of things: the message and builder classes, the class that holds a nested message's reader, whether the builder has a method, and whether messages of unknown classes may be read through `RuntimeReaders`. The plugin answers from `.proto` names; the runtime answers from the message class itself (`ProtobufJavaNames.messageClassOf` reads the accessors, so it is right whatever protoc did to avoid a name clash) and checks with reflection that every builder method the code calls exists with the exact signature — a field whose method is missing bails instead of failing the whole class.

### The run-time driver

`RuntimeCodegen.fastDecoder(messageClass, useCompiled)`:

1. plans the graph of message classes reachable through fields the template reads (cycles are fine: the classes refer to each other by name and are all defined before any is initialised);
2. runs the template per class and lowers it (`ClassBackend`, loaded by name so `buff-json` stays loadable on Java 21);
3. defines each class with `MethodHandles.privateLookupIn(messageClass, lookup()).defineClass` — same package, loader and protection domain as the message, so it links exactly like compiled code, and works when the application's classes are isolated from the library's (the only requirement is that the message's loader resolves buff-json, fastjson2 and protobuf-java to the very classes we use) — and initialises them, which is when the JVM verifies the bytecode;
4. publishes the decoders in a `ClassValue` slot per message class: no strong references from statics, so class loaders can still be unloaded and the generated classes go with them.

Two families exist, in two `ClassValue`s: *mixed* (`useCompiled = true`, the default when `setGeneratedDecoders(true)`): a child that has a plugin decoder calls that one (checked to be public, with a covariant `readFast`, visible to the message's loader); and *only* (`false`, used when `setGeneratedDecoders(false)`): everything is generated, plugin classes are ignored — tests and benchmarks use it to compare like with like.

Generation is serialised by one lock (first use of a type is rare; the lock keeps the graph planning simple and race-free). The hot path is a `ClassValue` lookup and a volatile read. A message class that cannot have a generated reader (not a public `GeneratedMessage`, no public builder, more than 800 fields, a loader that cannot see this library, a class the JVM refuses to define or verify) is remembered as such; a builder method that is missing only makes its own field bail.

The generated class is `public final class X$$BuffJsonFast implements BuffJsonGeneratedDecoder<Foo>` with a `public static final X INSTANCE`, the byte-exact enum name constants in its class initialiser, `readFast(FastInput)` (covariant, with the bridge javac would emit), and `readMessage`, which defers to the runtime decoder — the same the `readFast` falls back to. It is usable anywhere a plugin-generated decoder is.

Named classes were chosen over hidden classes on purpose: they can refer to each other by name (direct `invokestatic`/`getstatic`, inlined by the JIT, mutual recursion between message types), and they live and die with the message's class loader.

### Dispatch

`BuffJsonDecoder.decode(byte[] | String)` tries the plugin's reader (if `setGeneratedDecoders`), then a run-time generated one (if `setRuntimeCodegen`), then the general decoders. With `setGeneratedDecoders(false)` the whole graph is generated at run time, ignoring the plugin's classes.

### What is shared

|                         |                 build time (protoc plugin)                 |                         run time                          |
|-------------------------|------------------------------------------------------------|-----------------------------------------------------------|
| reader logic            | `FastReaderTemplate` → `SourcePrinter` → javac             | `FastReaderTemplate` → `ClassFileBackend` → `defineClass` |
| member-name matching    | `FieldNameMatcher.inlinePieces` (8/4/1-byte compares)      | the same                                                  |
| token/value helpers     | `FastInput` static helpers, `FastDouble`, `WellKnownTypes` | the same                                                  |
| what the class is about | `.proto` names → Java names (`Env`)                        | the message class itself, by reflection (`Env`)           |
| fallback                | generated `readMessage`                                    | typed-builder / descriptor decoders                       |

New code: the model (~780 lines), the printer (329), the template (834, replacing the 605-line string generator), the driver (516) and the backend (660, the only file that needs Java 24).

## Build and release

The backend needs the Class-File API, so its source lives in `buff-json/src/main/java24` and is compiled by a second `maven-compiler-plugin` execution with `release 24`, in the profile `classfile-codegen` that activates on JDK 24+ (`<jdk>[24,)</jdk>`). The classes land next to the Java 21 ones (class file major version 68, at the jar root) and are only ever loaded when `Runtime.version().feature() >= 24`. On a JDK 21 build the profile is off, the jar has no backend and `RuntimeCodegen.available()` is `false`.

- **Releases must be built on JDK 24+** to contain the backend (everything else is still compiled with `release 21`). `.github/workflows/release.yml` still builds on Java 21, so a release built there silently has no run-time generation. It needs a JDK 24+ (for example 25) to ship the feature; this change does not touch the release job.
- A multi-release jar was not used: `mvn test` in a reactor resolves module dependencies to `target/classes`, which does not honour `META-INF/versions`, so the tests of the other modules would never see the backend.
- CI: the build job runs on Java 21 and 25. On 25 a second `mvn verify -DargLine=-Dbuffjson.runtimeCodegen=true` runs the *whole* suite (every existing decode test) with run-time generation on by default.
- Diagnostics: `-Dbuffjson.codegen=false` disables it entirely (kill switch, also in case a future JDK breaks the backend), `-Dbuffjson.codegen.debug=true` prints why a message got no generated reader and how long each step took, `-Dbuffjson.codegen.dump=DIR` writes every generated class file (inspect with `javap -c -p`).

## Tests

Run-time generation is held to the same standard as the plugin's reader, and the model and backend are tested on their own:

- **Differential tests of the reader** (`FastPathTestBase`, 12 tests, run three times): canonical `JsonFormat`/BuffJson output (compact, pretty, proto field names) of random messages of 16 message types, including the official `TestAllTypesProto3`, must be *accepted* by the reader (otherwise it would silently never run) and exact; thousands of mutated, respelled and truncated documents and every single-byte damage to every member name must give the same message or the same exception type with the reader on and off, and whenever the reader accepts, the general decoder accepts with an equal result. The three subclasses select the reader under test: the **plugin** decoder (`BuffJsonFastPathTest`), a graph generated entirely **at run time** (`BuffJsonRuntimeFastPathTest`, compared with the typed-builder decoder), and the **mixed** family, where run-time generated readers call the plugin's (`BuffJsonMixedFastPathTest`). The run-time subclass adds `everyMessageTypeGetsAGeneratedDecoder` (no silent fallback) and `generatedAndPluginReadersAgreeOnEveryDocument` (compile-time and run-time readers accept and reject the same documents with equal results).
- **The model and the backend** (`CodegenModelTest`, 17 tests): the printer's parentheses and literals, and — by lowering small models and running them — every `int`/`long` operator and promotion, comparisons of every shape (systematically and as random nested boolean trees), short-circuiting, all switch shapes, `break`, arrays, strings, objects, and refusal of a method that can fall off its end.
- **Mutation check** of `ClassFileBackend`: 12 injected defects (negated comparison, `<=` as `<`, `> 0` as `>= 0`, `&&`/`||` dropping the right operand, `>>>` as `>>`, missing narrowing, switch fall-through, `long` compare without `lcmp`, wrong array kind, missing widening, reference `==` as `!=`). All are caught; the three that survived the first version of the tests each got a test of their own.
- **Foreign children** (`BuffJsonForeignChildrenTest`, 3 tests, `foreign_types.proto`): a plugin-generated parent whose children are messages the plugin never generated code for (`SourceContext`: singular, repeated, map value) decodes correctly in every configuration, and its own reader succeeds only where a run-time reader is allowed and possible. Writing this test exposed a bug in the plugin's general decoder (a missing cast when a nested message is read through the message reader, so such a field did not compile); it is fixed.
- **Class loaders and threads** (`BuffJsonCodegenLoaderTest`, 2 tests): a message class loaded by an isolating child class loader gets its reader (and its child's) defined in that loader; eight threads racing for the first use of such a class, half in each family, all get the same reader instance.
- **The existing suite** (629 tests with the new ones): passes unchanged on JDK 21 (41 tests skipped because they need Java 24+; the printer tests and everything else run) and on JDK 25 (none skipped). CI also runs the whole suite on JDK 25 with `-Dbuffjson.runtimeCodegen=true`, which makes every decoder that has no plugin reader — all the typed- and reflection-tier tests — offer each document to a run-time generated reader first; all of it passes, so the reader is exercised by every decode test in the project, not only by the tests written for it.

## Limits and risks

- **Opt-in.** Defaults to off: it changes which code runs for everyone who uses `setGeneratedDecoders(false)`, and defining classes into application class loaders at run time should be a decision. `-Dbuffjson.runtimeCodegen=true` flips the default for a whole JVM.
- **First-use latency.** ≈0.2–0.3 s for the first message class in a cold JVM (the Class-File API, the template and the printer run cold and dominate), then 10–30 ms per further message class and 60–100 ms for a message with 150 fields. Services that care can decode one representative document per type at start-up. Generation is synchronous; an asynchronous variant (decode with the typed decoder meanwhile) is a possible follow-up.
- **Java 24+ only**, at run time and for the build that produces the jar (see Build and release). Older JVMs work unchanged, with the typed decoder.
- **Not for GraalVM native images** (no class definition at run time). The typed decoder and the plugin's decoders are the native-image options.
- **Class loaders and modules.** The message's loader must resolve this library's classes to the same classes we use (guarded, otherwise the message is skipped). In a named module the message's package must be open to buff-json (`privateLookupIn`); otherwise generation fails and is recorded. Classes defined next to messages that come from another jar (e.g. protobuf-java's own well-known types) live in that jar's package, loader and protection domain.
- **Memory.** One small class per message class (see the bytecode column above), in the message's loader; freed with it.
- **What the model cannot express** (`float`/`double` comparison, `for`, `try`, lambdas, `invokedynamic`) makes the backend throw; generation then fails for that message class and the runtime decoders are used. The current template stays inside the subset, and the differential tests would notice otherwise (`everyMessageTypeGetsAGeneratedDecoder`).
- **Fast reader coverage** is that of the plugin's reader: no `Any`, `Struct`, `Value`, `ListValue`, `FieldMask` (a present member bails), at most 800 fields, no messages nested deeper than `FastInput.MAX_DEPTH` (100).

## Reproducing

```
# JDK 24+ needed for the backend (the tests skip themselves on 21)
mvn -B -ntp verify
mvn -B -ntp verify -DargLine=-Dbuffjson.runtimeCodegen=true      # whole suite through run-time generated readers

java -jar buff-json-benchmarks/target/benchmarks.jar DecodeCodegenBenchmark.utf8   -f 2 -wi 5 -w 1s -i 5 -r 1s
java -jar buff-json-benchmarks/target/benchmarks.jar DecodeCodegenBenchmark.string -f 2 -wi 5 -w 1s -i 5 -r 1s
java -jar buff-json-benchmarks/target/benchmarks.jar DecodeCodegenMixedBenchmark   -f 2 -wi 5 -w 1s -i 5 -r 1s

# see what is generated, and how long it takes
java -Dbuffjson.runtimeCodegen=true -Dbuffjson.codegen.debug=true -Dbuffjson.codegen.dump=/tmp/gen -cp ... YourMain
javap -c -p -cp /tmp/gen 'your.pkg.Message$$BuffJsonFast'
```

`DecodeCodegenBenchmark` runs the nine shapes of `DecodePathsBenchmark` with `mode=typed|runtime|plugin`; `DecodeCodegenMixedBenchmark` rotates six message types through one decoder (a service that decodes many types rather than one hot type).
